= ストレージ管理

Red Hat OpenShift は、オンプレミスとクラウドプロバイダーの両方に対応した多様なストレージをサポートしています。OpenShift Virtualization では、ワークロードが実行されている環境において、サポートされている任意のコンテナストレージインターフェース (CSI) プロビジョナーを使用できます。

物理ストレージシステムの例：Dell/EMC、Fujitsu、Hitachi、NetApp、Pure Storage など。

ソフトウェア定義ストレージ (SDS) の例：IBM Fusion Data Foundation、OpenShift Data Foundation (ODF)、Portworx など。

NOTE: このリストはすべてを網羅しているわけではありません。サポートされているすべてのストレージソリューションについては、**https://catalog.redhat.com/platform/red-hat-openshift/virtualization#virtualization-infrastructure[Red Hat EcoSystem Catalog^]** を参照してください。

このセクションでは、Persistent Volume Claims (PVC) について説明します。PVC はプロバイダーからストレージをリクエストし、VM ディスクを保存するために使用されます。多くのストレージプロバイダーは、デバイスレベルでのスナップショットとクローン機能もサポートしています。CSI ドライバーとストレージデバイスでサポートされている機能については、各ベンダーの仕様を確認してください。

OpenShift Virtualization では、特定のストレージプロトコル（NFS、iSCSI、FC など）に制限はありません。唯一の要件は、**RWX (ReadWriteMany) アクセスモード** が利用可能であることです。これはクラスター内の VM ライブマイグレーションをサポートするために不可欠です。それ以外については、組織の VM やアプリケーションのニーズに最適なストレージを選択してください。

== スナップショットの管理

OpenShift Virtualization は、CSI ストレージプロバイダーのスナップショット機能を利用して、VM ディスクのスナップショットを作成します。これは VM の稼働中（オンライン）または停止中（オフライン）のどちらでも実行可能です。VM に KVM 統合パッケージ (qemu-guest-agent) がインストールされている場合、ゲスト OS を自動的にクエスチング (Quiescing) するオプションが利用できます。これにより、ファイルシステムの一貫性が保たれた状態（バッファのフラッシュやジャーナルの一貫性確保）でスナップショットを取得できます。

スナップショットのパフォーマンスや容量への影響は、使用しているストレージプロバイダーの実装に依存します。詳細についてはストレージベンダーのドキュメントを確認してください。

IMPORTANT: スナップショット単体では、完全なバックアップやディザスタリカバリ (DR) 機能は提供されません。通常、スナップショットは元のボリュームと同じ物理ストレージ上に保存されるためです。真の DR 対策としては、別の場所へのデータコピーの保存や、遠隔地のストレージへのミラーリングが必要です。

VM スナップショット機能により、管理者は以下の操作が可能になります：

* 新しいスナップショットの作成
* VM に紐づくスナップショットの一覧表示
* スナップショットからの VM 復元
* 既存のスナップショットの削除

=== スナップショットの作成と使用

. *仮想化 (Virtualization)* パースペクティブに戻り、左メニューの *VirtualMachines* をクリックします。中央のセクションでプロジェクト *vmexamples-{user}* を選択し、*fedora01* 仮想マシンをクリックします。
+
image::2025_spring/module-04-storage/03_VM_Overview.png[link=self, window=blank, width=100%]

. 現在、この VM にはスナップショットが作成されていないことが確認できます。
+
image::2025_spring/module-04-storage/04_Snapshots_Overview.png[link=self, window=blank, width=100%]

. ページ上部の *Snapshots* タブに移動します。
+
image::2025_spring/module-04-storage/05_Snapshot_Menu.png[link=self, window=blank, width=100%]

. *Take snapshot* をクリックしてダイアログを開きます。
+
image::2025_spring/module-04-storage/06_VM_Snapshot_Dialog.png[link=self, window=blank, width=100%]
+
NOTE: `cloudinitdisk` がスナップショットに含まれないという警告が表示されますが、これはブート用のエフェメラルディスク（一時ディスク）であるための想定通りの挙動です。

. 名前を確認し、*Save* をクリックします。ステータスが *Operation complete* になるまで待ちます。
+
image::2025_spring/module-04-storage/07_VM_Snapshot_Taken.png[link=self, window=blank, width=100%]

. 3 点リーダー（メニュー）をクリックすると、VM が実行中のため *Restore* オプションがグレーアウトされていることがわかります。
+
image::2025_spring/module-04-storage/08_VM_Restore_Disabled.png[link=self, window=blank, width=100%]

. *Console* タブに切り替え、VM にログインします。ここでは意図的に OS を破壊し、ブートできない状態にします。
+
image::2025_spring/module-04-storage/09_Console_Login.png[link=self, window=blank, width=100%]
+
NOTE: ID/パスワード横のコピーアイコンや「Paste to console」ボタンを使うと便利です。

. ログイン後、以下のコマンドを実行してブートローダーを削除し、再起動します：
+
[source,sh,role=execute]
----
sudo rm -rf /boot/grub2; sudo shutdown -r now
----

. 再起動後、OS が正常にブートできなくなっていることを確認します。
+
image::2025_spring/module-04-storage/10_Bootloader_Broken.png[link=self, window=blank, width=100%]
+
IMPORTANT: 前のステップでシャットダウンを実行しましたが、OpenShift Virtualization のデフォルト設定により、VM は自動的に再起動されます。この挙動は必要に応じて変更可能です。

. *Actions* メニューまたは右上のボタンを使用して、VM を停止 (*Stop*) します。OS が不安定なため通常の停止に時間がかかる場合は、再度メニューから *Force stop*（強制停止）を選択してください。

. *Overview* タブで VM が停止したことを確認します。
+
image::2025_spring/module-04-storage/11_VM_Stopped_Snapshot.png[link=self, window=blank, width=100%]

. スナップショットタイルの 3 点リーダーをクリックします。VM が停止したため *Restore* が選択可能になっています。クリックします。
+
image::2025_spring/module-04-storage/12_VM_Restore.png[link=self, window=blank, width=100%]

. ダイアログが表示されたら *Restore* をクリックします。
+
image::2025_spring/module-04-storage/13_VM_Restore_Dialog.png[link=self, window=blank, width=100%]

. 復元が完了するまで待ちます（通常はすぐに完了します）。上部の *Snapshots* タブで復元操作の詳細を確認できます。
+
image::2025_spring/module-04-storage/14_VM_Restored.png[link=self, window=blank, width=100%]

. *Overview* タブに戻り、VM を開始します。
+
image::2025_spring/module-04-storage/15_VM_Start.png[link=self, window=blank, width=100%]

. *Console* タブで、OS が正常にブートすることを確認してください。
+
image::2025_spring/module-04-storage/16_VM_Running.png[link=self, window=blank, width=100%]

== 仮想マシンのクローン作成

クローン作成は、既存の VM のディスクイメージや設定、データを引き継いだ新しい VM を作成する機能です。

. *Overview* 画面の *Actions* ドロップダウンメニューから *Clone* を選択します。
+
image::2025_spring/module-04-storage/17_Overview_Actions_Clone.png[link=self, window=blank, width=100%]

. 名前を *fedora02* とし、*Start VirtualMachine on clone*（クローン後に起動）にチェックを入れた状態で *Clone* をクリックします。
+
image::2025_spring/module-04-storage/18_VM_Clone_Dialog.png[link=self, window=blank, width=100%]

. 新しい VM が作成され、自動的にその詳細ページに切り替わります。
+
image::2025_spring/module-04-storage/19_VM_Cloned.png[link=self, window=blank, width=100%]
+
IMPORTANT: クローンされた VM はソース VM と全く同じ識別情報（ホスト名など）を持っているため、同一ネットワーク内で競合が発生する可能性があります。外部ネットワーク接続時は特に注意してください。

. ページ上部の *YAML* タブをクリックします。VM 名は `fedora02` になっていますが、ソース VM から引き継がれたラベルなどは手動で更新するのがベストプラクティスです。
+
image::2025_spring/module-04-storage/20_Cloned_VM_YAML.png[link=self, window=blank, width=100%]

. YAML 内の `app` および `kubevirt.io/domain` の値を `fedora02` に変更し、下部の *Save* をクリックします。これにより、以降のモジュールでの不要なトラブルを避けることができます。
+
image::2025_spring/module-04-storage/21_Cloned_VM_YAML_Saved.png[link=self, window=blank, width=100%]

. YAML の変更を保存したら、VM を起動し、*fedora01* と *fedora02* の両方が正常に稼働している状態にします。
+
image::2025_spring/module-04-storage/22_Fedora02_Running.png[link=self, window=blank, width=100%]

== まとめ

このセクションでは、VM 管理におけるストレージオプションと、ストレージ機能を活用した管理操作（スナップショットによる復元、クローン作成）について学習しました。これらの機能は、運用の効率化や開発環境の迅速な展開に非常に役立ちます。
